# CircleCI

This pipeline runs the pull-request CI **alongside** the GitHub Actions workflows
in `.github/workflows/`. Nothing has been removed from Actions, and nothing here
publishes: releases stay on `release.yml`.

Modeled on [palantir/blueprint]'s config, the closest Palantir-run precedent for a
pnpm monorepo on CircleCI.

[palantir/blueprint]: https://github.com/palantir/blueprint/blob/develop/.circleci/config.yml

## Remaining steps

**`GITHUB_TOKEN` — optional.** Only `bundle-size` needs it, to post its
size-limit comparison as a PR comment. Without it the report prints to the job
log instead.

Set it as a plain project environment variable, which is what Blueprint does, or
as an org context, in which case add `context: <name>` to the `bundle-size` entry
under `workflows:`. It needs `pull-requests: write`; unlike Actions, CircleCI has
no automatic per-run token, so prefer a machine account or App over a personal
PAT.

**Never enable "Pass secrets to forked pull requests."** That hands the token to
arbitrary contributors.

**Branch protection: do not change it yet.** The Actions checks stay
authoritative while this bakes. When the time comes, `ci-all` is the single check
to require, since it fans in from every other job.

## Traps

The things most likely to get undone by accident.

**Storybook's base path must stay relative.** `STORYBOOK_BASE_PATH: ./` becomes
vite's `base`. CircleCI serves artifacts under a long path prefix, so any absolute
base — vite's default `/`, or `.storybook/main.ts`'s gh-pages path — makes
`index.html` request `/assets/...` from the host root and 404. That is the
difference between a browsable preview and a downloadable zip. Blueprint sets no
base and has this problem.

**Never move the JUnit reporter into a `turbo run test -- …` passthrough.** Turbo
folds passthrough arguments into its _global_ hash, so passing them makes every
task in the run a cache miss, not just `test`. When that was the mechanism, the
test jobs discarded the build cache and rebuilt the whole graph. The reporter
lives in each `vitest.config.mts` instead, generated by the `fileContents` rule in
`.monorepolint.config.mjs` — change the generator and run `mrl check --fix`, not
the 87 files. `@osdk/maker` is in that rule's `excludePackages` and is kept in
sync by hand.

**`store_test_results` and `store_artifacts` do not accept `when: always`.** Their
schema sets `additionalProperties: false`, and `circleci config validate` passes
it through silently, so nothing in CI catches it. Both test jobs instead record
the test exit code and re-raise it in a final step, which is what gets reports
uploaded on a failing run.

**`classnameTemplate` is a junit _reporter_ option, not a `test`-level one.**
Setting it at `test:` level is a silent no-op. It prefixes each classname with the
package directory, because CircleCI keys a test on `(classname, name)` and
vitest's default classname is package-relative — `src/junk.test.ts` exists in both
`@osdk/api` and `@osdk/version-updater`, and 13 paths collide this way. Unprefixed,
flaky detection reads "passed here, failed there" as one flaky test.

**`cimg/node` publishes no bare major tags.** `cimg/node:24` is a 404, not a float
to the newest 24.x, so the matrix pins `MAJOR.MINOR`. This is the one place where
reasoning by analogy from Actions misleads: `actions/setup-node` resolves
`node-version: 24`, but a docker tag is a literal. Two consequences — these go
stale at the minor boundary and there is no Renovate config here to bump them, and
the `test` job selects the Node 18 excludes with a `case` on the major rather than
an equality test, since `= "18"` stops matching the moment the minor moves.

**`reports/` must stay gitignored, and `turbo.json` must keep `outputs: ["reports/**"]` on `test`.** Without the output declaration a cache hit replays
logs and writes no file; without the gitignore, turbo folds the untracked XML into
each package's input hash and every test task misses on the following run.
`env: ["FORCE_COLOR", "CI"]` is there because the vitest config switches on `CI`.

## Deciding what needs to run

`scripts/is-affected.sh` answers "does this package need rebuilding or
retesting?" by asking turbo's package graph rather than matching paths. A path
pattern is transitively blind: a change to `@osdk/client` reaches a story through
imports, and no glob over `packages/react-components*` would see it.
`storybook-interaction-tests` uses it.

It builds on `scripts/base-ref.sh` and **fails open** — an unresolvable base means
do the work, because skipping a job we needed is worse than running one we did
not.

Any root-level file change marks turbo's root package `//` as changed, so a bare
`--affected` behaves surprisingly on a CI-config PR.

## Notes on the mirror

| Actions                              | Here                                                                                                                                                                  |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `github.event.pull_request.base.sha` | `scripts/base-ref.sh`, which resolves the merge-base with `main` and exits 2 when it cannot.                                                                          |
| `if:` on branch                      | Job-level `filters: branches: ignore:`, on `changesets` and `bundle-size`. Safe only because neither gates `ci-all`; a filtered-out job blocks anything requiring it. |
| `services:` container                | A second image in the job's `docker:` list (`e2e` + verdaccio), plus a readiness poll, since these have no healthcheck.                                               |
| `actions/cache` `restore-keys`       | `restore_cache` with an ordered `keys:` list.                                                                                                                         |

Two deliberate divergences beyond Storybook:

- **No infra-change `--force` detection.** `ci.yml` forces a clean build when
  certain files change. Turbo already tracks them: a semantic `pnpm-lock.yaml`
  edit moves `transpileEsm`'s hash, and `turbo.json`, `package.json` and
  `babel.config.mjs` are in turbo's global hash. Worth knowing that
  `config/tsconfig.base.json`, in `ci.yml`'s list, does not exist and never has.
- **`changesets` does not gate `ci-all`**, matching Actions, whose `ci-build`
  needs `changes` — the package-detection job — not `changesets`.

## Performance shape

| Class  | Jobs                                                                              | Why                                                               |
| ------ | --------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| xlarge | `build`, `typecheck`, `lint`, `build-apps`, `test`, `storybook-interaction-tests` | Genuinely parallel; oxlint/oxfmt are Rust and scale across cores. |
| large  | `install`, `e2e`, `bundle-size`, `build-storybook`                                | I/O bound, or single-threaded where it matters (Rollup).          |
| medium | `changesets`, `cspell`                                                            | Short and mostly single-task.                                     |
| small  | `ci-all`                                                                          | An `echo`.                                                        |

- **One install.** Only `install` runs `pnpm install`; everything else attaches
  `node_modules` from the workspace, trading a ~1.1 GB upload for fifteen fewer
  installs. `bundle-size` is the exception, since it reinstalls against the base
  commit's lockfile. The same install serves all four Node legs, which is safe
  because the native dependencies are N-API; a "cannot load native module" failure
  on one leg would mean that assumption broke.
- **The turbo cache travels through the workspace**, so downstream jobs get _this_
  pipeline's artifacts rather than guessing at an earlier pipeline's cache key.
- **`bundle-size`'s base measurement is cached** on the base commit SHA, so only
  the first push to a PR pays for it.
- **Chromium is paid for once.** Installing it is two costs: `--with-deps` runs
  `apt-get`, and `playwright install` downloads Playwright's own pinned build.
  `cimg/node:24.19-browsers` covers the first, a cache on
  `~/.cache/ms-playwright` the second. Watch that the larger image's pull does not
  eat the saving.
- **`test` runs `parallelism: 2`**, so the matrix is 8 containers. Container 1
  runs `@osdk/react-components` alone: that suite starves its own vitest main
  thread against ~80 other test processes and trips the worker RPC timeout.

On whether the long jobs should use more `parallelism`: a job costs `F + D/N`,
fixed setup plus divisible work, and `parallelism` duplicates the setup —
including the workspace attach — on every container. It only pays when the
divisible part dominates, which for `e2e` it does not.

## Coverage

Not collected here. `scripts/coverage/collect.sh` remains the local tool and
passes its own CLI flags. Turning it on in CI needs the workspace to agree on a
vitest major first: `@vitest/coverage-v8` is pinned `^3.2.4` at the root while two
packages are on `vitest@4`, and a 3.x provider driving a 4.x runner dies in
`getUntestedFiles`. The provider is only loaded when coverage is on, so that skew
stays invisible until someone tries. Re-enabling is one `COVERAGE=true` export.

## Possible follow-ups

- Run the full Node matrix only on `main` and just 18 + 24 on PRs. Halves the
  matrix cost, but it is a real coverage reduction.
- Split the base-branch build out of `bundle-size` so the two measurements can run
  concurrently.

## Validating changes

```sh
circleci config validate .circleci/config.yml   # needs `circleci auth login`
circleci config process .circleci/config.yml    # shows the expanded graph
shellcheck .circleci/scripts/*.sh
pnpm exec mrl check                             # the generated vitest configs
```

# CircleCI

This pipeline runs the pull-request CI **alongside** the GitHub Actions workflows
in `.github/workflows/`. Nothing here has been removed from Actions, and nothing
here publishes: releases stay on `release.yml`.

The config was modeled on [palantir/blueprint]'s, the closest Palantir-run
precedent for a pnpm monorepo on CircleCI.

[palantir/blueprint]: https://github.com/palantir/blueprint/blob/develop/.circleci/config.yml

## Remaining steps

Neither can be set from a commit, and neither blocks anything: the pipeline runs
without them.

### 1. `GITHUB_TOKEN` — only for PR comments

Optional. Everything runs without it; the only difference is that the two jobs
that want to write to the PR print to the job log instead:

- `bundle-size` posts its size-limit comparison as a sticky comment.
- `fork-guard` reads the `safe-to-test` label as a bypass, so without a token it
  fails any fork PR touching sensitive paths rather than honouring the label.

Set it as a plain project environment variable, which is what Blueprint does, or
as an org context — in which case add `context: <name>` to the `bundle-size` and
`fork-guard` entries under `workflows:`, since the config references no context.

It needs `pull-requests: write` and `issues: read` (for the label check). A
fine-grained PAT or a GitHub App installation token both work; unlike Actions,
CircleCI has no automatic per-run token. Prefer a machine account or App over a
personal PAT, since comments post under whoever owns the token.

**Never enable "Pass secrets to forked pull requests"** to make this work on
forks. That hands the token to arbitrary contributors.

### 2. Branch protection — do not change it yet

**Leave the required status checks exactly as they are.** The Actions checks stay
authoritative while this bakes. CircleCI's appear as `ci/circleci: <job>` and are
informational until someone deliberately promotes them.

When the time comes, `ci-all` is the single check to require: it fans in from
every other job. Promote it, watch a few PRs, then retire the Actions equivalents
one at a time.

## What this does differently from GitHub Actions

Everything is a faithful mirror of `ci.yml` except Storybook.

On Actions, `storybook-preview.yml` builds Storybook and force-pushes it to a
`gh-pages` directory, while `ci.yml`'s `build-apps` builds the same Storybook
again. So it is built twice per PR, previews accumulate in git history, and the
force-pushes race `deploy-docs.yml` and `deploy-storybook.yml` for one branch.

Here it is built once, in `build-storybook`, and stored as a **navigable
artifact** — the preview is a link on the job. `build-apps` excludes the package
so the two cannot both build it.

There is still **no visual regression testing**, same as on Actions. Chromatic
was prototyped here and removed: it was never part of the Actions setup and
nothing is configured for this project. `storybook-interaction-tests` covers
behavior, not appearance.

### Browsable Storybook artifacts

Being _navigable_ rather than merely downloadable hinges on
`STORYBOOK_BASE_PATH: ./`, which becomes vite's `base`. CircleCI serves artifacts
under a long path prefix, so any absolute base — vite's default `/`, or
`.storybook/main.ts`'s gh-pages path — makes `index.html` request `/assets/...`
from the host root and 404.

Worth knowing because it is a natural thing to copy: **Blueprint does not do
this**, so its own artifact has the same problem. If the artifact ever goes blank
with 404s on `assets/*`, this line is the first thing to check.

## Test results

`test` and `storybook-interaction-tests` emit JUnit XML, which gives CircleCI a
Tests tab with individual test names and durations, and enables flaky detection.

A failing run is when the report matters most, so both jobs record the test exit
code, let the uploads run, and re-raise it in a final step. **This cannot be done
with `when: always`**: CircleCI's schema allows `when` on `run` and `save_cache`,
but `store_test_results` and `store_artifacts` set `additionalProperties: false`
and reject it — and `circleci config validate` passes it through silently, so the
mistake is invisible in CI.

Four things make the reporting work, and all four are load-bearing:

- **The reporter is configured per package, not on the command line.** Each
  `vitest.config.mts` sets `reporters` and `outputFile`, generated by the
  `fileContents` rule in `.monorepolint.config.mjs`. Change the generator and run
  `mrl check --fix`, not the 80-odd files. `@osdk/maker` is in that rule's
  `excludePackages` and is kept in sync by hand.

  **This must never move into a `turbo run test -- …` passthrough.** Turbo folds
  passthrough arguments into its **global** hash, so every task in the run
  becomes a cache miss, not just `test`. When that was the mechanism, the test
  job discarded the build cache and rebuilt the whole graph inside the test
  container.
- **`turbo.json` declares `"env": ["FORCE_COLOR", "CI"]`** on `test`, because the
  config above switches on `CI`. Without it a cache entry created locally (no
  XML) could be restored in CI and the upload would be silently empty.
- **`turbo.json` declares `"outputs": ["reports/**"]`** on `test`. Without it a
  cache hit replays the logs and writes no file.
- **`reports/` is gitignored.** Turbo folds untracked, non-ignored files into a
  package's input hash, so leaving the XML visible makes every test task a cache
  miss on the run after it emits a report.

`scripts/collect-test-results.sh` gathers the per-package reports into one
directory, because `store_test_results` takes a path rather than a glob. On the
way through it prefixes each `classname` with its package: vitest sets classname
to the package-relative file path, and 13 of those are duplicated across packages
(`src/junk.test.ts` is in both `@osdk/api` and `@osdk/version-updater`).
Unprefixed, flaky detection would read "passed here, failed there" as one flaky
test.

Packages without a `vitest.config.mts` emit no JUnit: the `examples/*` packages
and the four `tests/verify-*` ones whose `test` script is `webpack` or plain
`node`. That is also why the reporter cannot be a blanket CLI flag — webpack
rejects `--reporter=junit` outright.

Note pnpm 10 does **not** forward arguments after a `--` separator, so the
Storybook invocation passes them directly after the script name.

### Coverage

**Off, and blocked on a dependency question rather than on CI.**
`@vitest/coverage-v8` is pinned `^3.2.4` at the root while two packages are on
`vitest@4`. A 3.x provider cannot drive a 4.x runner — it dies in
`getUntestedFiles` — and the provider is only loaded when coverage is on, so the
skew is invisible until then.

Re-enabling is one line, a `COVERAGE=true` export in the `test` job, but not
until the workspace agrees on a vitest major; bumping the root provider to 4.x
just moves the breakage onto the ~45 packages still on 3.

Everything else stays wired and inert: the generated configs read `COVERAGE`,
turbo hashes it and declares `coverage/**` as a `test` output, and the merge and
artifact steps remain. That output declaration is worth keeping regardless —
`scripts/coverage/collect.sh` only uses `--force` because coverage output was
undeclared.

## Asking "did this change?"

Two different questions, two different tools, and mixing them up causes real
bugs:

- **"Which files changed?"** — `scripts/changed-files.sh`, for questions genuinely
  about paths. `fork-guard` uses it.
- **"Does this package need rebuilding or retesting?"** —
  `scripts/is-affected.sh`, which asks turbo's package graph. A path pattern is
  transitively blind: a change to `@osdk/client` reaches a story through imports,
  and no glob over `packages/react-components*` would see it.
  `storybook-interaction-tests` uses it.

Both build on `scripts/base-ref.sh` and both **fail open** — an unresolvable base
means do the work, because skipping a job we needed is worse than running one we
did not.

Any root-level file change (including `.circleci/**`) marks turbo's root package
`//` as changed, so a bare `--affected` behaves surprisingly on a CI-config PR.

## Notes on the mirror

Where CircleCI has no direct equivalent of an Actions feature:

| Actions                               | Here                                                                                                                                                                        |
| ------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `github.event.pull_request.base.sha`  | `scripts/base-ref.sh`, which resolves the merge-base with `main`. Exits 2 when it cannot, and every caller fails open.                                                      |
| `if:` job conditions on branch        | Job-level `filters: branches: ignore:`, used by `changesets` and `bundle-size`. Only safe because neither gates `ci-all` — a filtered-out job blocks anything requiring it. |
| `if:` job conditions on event payload | `fork-guard` calls `circleci-agent step halt`, which ends the job **successfully** so `ci-all` stays reachable.                                                             |
| `services:` container                 | A second image in the job's `docker:` list (`e2e` + verdaccio), plus an explicit readiness poll — these have no healthcheck.                                                |
| Matrix `node-version: 18`             | `cimg/node:18.20`. Not `cimg/node:18` — see below.                                                                                                                          |
| `actions/cache` `restore-keys`        | `restore_cache` with an ordered `keys:` list.                                                                                                                               |

### Node image tags

**`cimg/node` publishes no bare major tags.** `cimg/node:24` is a 404, not a
float to the newest 24.x.

This is the one place where reasoning by analogy from Actions actively misleads:
`actions/setup-node` takes `node-version: 24` and _resolves_ it, because it is a
version resolver. A Docker tag is a literal that either exists or does not. The
first version of this config assumed otherwise and every job failed to pull.

So the matrix pins `MAJOR.MINOR`, the coarsest tag that exists. Two consequences:
these go stale at the minor boundary (`24.19` never becomes `24.20`, and there is
no Renovate config here to bump it), and the `test` job selects the Node 18
excludes with a `case` on the major rather than an equality test — `= "18"` would
silently stop matching the moment the pinned minor moved.

Blueprint pins exact patches, which is the more deterministic option if a
floating patch ever turns CI red on its own.

## Performance shape

Resource classes are deliberate, not uniform:

| Class  | Jobs                                                                              | Why                                                               |
| ------ | --------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| xlarge | `build`, `typecheck`, `lint`, `build-apps`, `test`, `storybook-interaction-tests` | Genuinely parallel; oxlint/oxfmt are Rust and scale across cores. |
| large  | `install`, `e2e`, `bundle-size`, `build-storybook`                                | I/O bound, or single-threaded where it matters (Rollup).          |
| medium | `changesets`, `cspell`                                                            | Short and mostly single-task.                                     |
| small  | `fork-guard`, `ci-all`                                                            | A `git diff` and an `echo`.                                       |

What keeps the cost down:

- **One install.** Only `install` runs `pnpm install`; everything else attaches
  `node_modules` from the workspace, trading a ~1.1 GB upload for fifteen fewer
  installs. `bundle-size` is the exception, since it must reinstall against the
  base commit's lockfile.
- **The turbo cache travels through the workspace**, so downstream jobs get _this_
  pipeline's artifacts rather than guessing at an earlier pipeline's cache key.
- **`bundle-size`'s base measurement is cached** on the base commit SHA, so only
  the first push to a PR pays for it.
- **Chromium is paid for once.** Installing it is two costs: `--with-deps` runs
  `apt-get`, and `playwright install` downloads Playwright's own pinned build.
  Removing one leaves the step slow. The job uses `cimg/node:24.19-browsers` for
  the system libraries and caches `~/.cache/ms-playwright` for the download.
  Watch that the larger image's pull does not eat the saving; if it does, keep
  the cache and go back to the plain image with `--with-deps`.

Two deliberate costs, both accepted:

- `test` runs `parallelism: 2`, so the matrix is 8 containers rather than 4.
  Container 1 runs `@osdk/react-components` alone: that suite starves its own
  vitest main thread when competing with ~80 other test processes and trips the
  worker RPC timeout. Actions works around it by running it serially afterwards;
  its own container removes the contention and runs it concurrently.
- A single install serves all four Node legs. Safe because the native
  dependencies are N-API, whose ABI is stable across Node majors. A "cannot load
  native module" failure on one leg would mean that assumption broke.

On whether the long jobs should use `parallelism`: a job costs `F + D/N`, fixed
setup plus divisible work, and `parallelism` duplicates the setup — including the
workspace attach — on every container. It only pays when the divisible part
dominates, which for `e2e` it does not: `changeset version` rewrites every
manifest in one pass and would run identically on each container.

## Possible follow-ups

- Run the full Node matrix only on `main` and just 18 + 24 on PRs. Halves the
  matrix cost, but it is a real coverage reduction.
- Split the base-branch build out of `bundle-size` so the two measurements can
  run concurrently.

## Validating changes to this config

```sh
circleci config validate .circleci/config.yml   # needs `circleci auth login`
circleci config process .circleci/config.yml    # shows the expanded graph
shellcheck .circleci/scripts/*.sh
```
